ASSURANCE REGENT v6.1.0 — SCALABILITY & RESILIENCE DEPLOYMENT GUIDE
====================================================================

PURPOSE
-------
v6.1.0 preserves the complete v6.0 Recovery Assurance & Accounting release and adds
traffic management, database hot-path indexes, bounded browser networking, request
coalescing/caching, coalesced state saves, multi-tab worker leadership, incident
monitoring, health analytics and Jivan safe recovery.

DEPLOYMENT ORDER
----------------
1. Confirm all migrations required through v6.0.0 are already installed.
2. In Supabase SQL Editor run:
     SCALABILITY_RESILIENCE_V6_1_0.sql
3. Run:
     SCALABILITY_RESILIENCE_V6_1_0_VERIFY.sql
   The result should show schemaVersion 6.1.0 and ready=true.
4. Replace/deploy the Supabase Edge Function named "recovery-agent" using:
     RECOVERY_AGENT_EDGE_FUNCTION.ts
   The same source is also supplied at supabase/functions/recovery-agent/index.ts.
5. Deploy the v6.1.0 public build to Netlify/GitHub.
6. Hard-refresh once after deployment.

WHAT CHANGED FOR SCALE
----------------------
- Browser request pool limits simultaneous requests to 6 per tab.
- Safe read RPC calls are deduplicated while in flight and briefly cached.
- Transient read failures use bounded timeout/backoff/retry instead of request storms.
- Full-state saves are debounced and coalesced so rapid UI changes do not create an
  unbounded chain of writes.
- A browser-tab lease elects one active worker tab per signed-in account in a browser profile to run Jivan
  background-queue polling and resilience monitoring, reducing duplicate work when
  the same user opens several Assurance Regent tabs.
- Session/control/health polling is slower, visibility-aware and jittered so many
  clients do not hit Supabase at exactly the same second.
- Database indexes were added to authentication sessions, credentials, Jivan
  conversations/tasks/audits, leave/work status and Recovery Assurance hot paths.
- Server-side per-user rate-limit buckets protect Jivan/expensive operations from
  bursts that could consume shared capacity.
- Netlify keeps hashed JS/CSS/assets immutable while index.html revalidates, reducing
  repeat bandwidth without causing stale application shells.

JIVAN SYSTEM HEALTH / SAFE RECOVERY
-----------------------------------
Developer, CEO and Administrator authority can use Assurance Engine > System Health.
Jivan can inspect the same bounded health summary when authorized.

Jivan may safely:
- detect and record transient client/API failures;
- report concurrent sessions, Jivan queue depth, stale tasks, recent errors and
  legacy shared-state payload size;
- requeue stale RUNNING Jivan background tasks automatically;
- open System Health and explain incidents;
- Developer only: purge already-expired sessions and old rate-limit buckets.

Jivan may NOT treat these as automatic "repairs":
- rewriting production JavaScript/TypeScript;
- changing SQL/RLS/security policies;
- altering account authority;
- changing payroll, HR, donor, evidence, approval or journal records;
- dropping/truncating data;
- bypassing human financial approvals;
- claiming to repair Supabase/OpenAI/ISP outages while those services are unavailable.
Those cases are diagnosed and escalated for a controlled deployment/human decision.

CAPACITY NOTE
-------------
v6.1 substantially reduces request amplification and database contention, but no
credible fixed concurrent-user number can be promised without load testing against
the actual Supabase/Netlify/OpenAI plans and real data volume.

The original browser-client operational store still contains a legacy shared JSONB
state row. v6.1 protects it with coalesced writes and monitors its byte size. The
newer high-value modules (Jivan tasks/messages, leave/work status and Recovery
Assurance) already use dedicated tables. For very large long-term deployments, the
next structural scaling step is to migrate remaining high-write legacy operational
collections into normalized, company-scoped tables with server-side cursor
pagination. System Health raises STATE_GROWTH_REVIEW when the legacy state becomes
large so this migration can happen before performance is affected.

RECOMMENDED VALIDATION
----------------------
- Open several Assurance Regent tabs: only one tab should actively claim Jivan
  background work at a time.
- Generate rapid edits: latest state should be saved without a growing write queue.
- Open System Health as Developer/CEO/Admin and verify metrics load.
- Create a background task, interrupt it long enough to become stale in a test
  environment, then verify safe requeue.
- Confirm Employee/Finance/Auditor users cannot execute System Health recovery RPCs.
- Confirm Recovery Assurance, voice conversation, HR, leave, uploads and governance
  continue to operate unchanged.
