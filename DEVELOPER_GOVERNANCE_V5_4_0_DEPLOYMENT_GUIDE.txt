ASSURANCE REGENT v5.4.0 — DEVELOPER ACCOUNT GOVERNANCE

WHAT THIS RELEASE ADDS
- Every Administrator/Employee self-registration is created as PENDING and cannot sign in until a Developer confirms it.
- Pending account requests appear in the Developer Notifications panel with Confirm and Reject actions.
- Developers can create already-approved Employee, Administrator, or Developer accounts.
- Developers can promote an existing approved account to Developer. Administrators cannot grant Developer authority.
- Developers can approve/activate, reject, suspend, delete, and reset passwords for managed accounts.
- Developers get a company service directory with an ON/OFF toggle, monthly amount, currency, payment account/instructions, and an optional billing message.
- Switching a company OFF blocks its Administrators and Employees at the database RPC layer without deleting their data.
- When blocked, users see: “Company access is offline. Pay <currency> <amount> and the system will be online again.” plus configured payment details/message.
- Switching the company back ON restores access to the same stored data.
- Developer account Dvp remains protected from deletion/suspension.

DEPLOYMENT — EXISTING v5.3.1 DATABASE
1. Open Supabase Dashboard > SQL Editor > New query.
2. Open DEVELOPER_GOVERNANCE_V5_4_0.sql from this package.
3. Copy ALL SQL and Run it. Run this governance script LAST, after any older Recovery Agent SQL upgrades.
4. Run DEVELOPER_GOVERNANCE_V5_4_0_VERIFY.sql. Confirm schemaVersion 5.4.0 and governanceReady=true.
5. Replace the GitHub/Netlify website files with this v5.4.0 package and deploy.
6. Hard-refresh the deployed site.

NEW DATABASE
1. Run ASSURANCE_REGENT_SUPABASE_SETUP.sql from this package. It already includes the v5.4.0 governance layer at the end.
2. If you separately run an older RECOVERY_AGENT_* SQL file afterwards, run DEVELOPER_GOVERNANCE_V5_4_0.sql again LAST so the governance-aware session/agent functions remain the final definitions.
3. Deploy the existing recovery-agent Edge Function and website as before. No OpenAI secret changes are required for this release.

TEST PLAN
A. Self-registration approval
1. Sign out. Create an Employee account with a valid Developer-created company code.
2. The registration should finish with a message that Developer approval is required. It must NOT log the new user in.
3. Try to sign in with that account. It should report that approval is pending.
4. Sign in as Developer. Open Notifications. The request should show Confirm and Reject.
5. Confirm it. Sign out and sign in with the new account; access should now work.

B. Developer delegation
1. As Developer, open Control Center > Settings.
2. Under Create approved account, choose Developer, enter the new Developer identity/password, and create it.
3. Sign out and sign in using User type Developer and the new credentials.
4. Confirm the new Developer can manage account approvals and company service controls.

C. Account suspension/password
1. Developer > Settings > Access, approvals & company directory.
2. Select an account, suspend it, and verify it can no longer use the system.
3. Activate it again.
4. Set a new password and verify the new password works.

D. Company service OFF/ON
1. In the Developer company service directory, set monthly amount, currency, payment instructions and optional message.
2. Toggle the company OFF.
3. Within the next refresh/session check, company Administrators/Employees should be returned to sign-in with the billing/offline message.
4. Their records remain in Supabase.
5. Toggle the company ON and verify those users can sign in and continue with their previous data.

SECURITY BOUNDARIES
- Approval, Developer assignment, user suspension/deletion/password reset and company-wide service control are enforced by SECURITY DEFINER RPC functions that validate the Assurance Regent session and actor role.
- Administrators cannot promote anyone to Developer and cannot alter the global company directory.
- Ordinary state writes can no longer replace the auth/company directory unless the signed-in actor is a Developer.
- Recovery Agent context/thread RPCs also pass through the same account/company gate, so a disabled company cannot use the AI route as a bypass.
